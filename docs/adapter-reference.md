# Справочник адаптера Astra MCP

Подробности конфигурации, XML-контракта и выполнения заданий. Начало работы и обзор проекта — в [README](../README.md).

Локальный MCP-сервер для агентов: исходный XML заказа → установленная Астра Раскрой → сохранённый XML результата. Сервер использует файловый обмен и командную строку `-i -n -q`. DLL SDK не требуется. Готовые решения PromCut в Астру не передаются.

Проект является отдельным Git-репозиторием. Решение `AstraMcp.sln` содержит `Core`, `Infrastructure`, `Mcp`, отдельный проект `Tests`, тестовый дочерний процесс `NativeFixture` и .NET-клиент проверки `tools/Verification`. C#/.NET 10, DI через Generic Host, официальный `ModelContextProtocol` **2.3.0**, атрибуты `[McpServerToolType]`/`[McpServerTool]`, `WithToolsFromAssembly()` и ресурсы с `WithResourcesFromAssembly()`.

## Запуск

Опубликованное приложение `publish/win-x86/AstraMcp.exe` содержит .NET runtime. На машине запуска нужна установленная Астра и интерактивная сессия Windows. MCP-клиент запускает сервер через stdio; сетевой порт не открывается. Сохраняйте соединение во время активного расчёта: остановка MCP прерывает принадлежащий ему дочерний процесс.

Пример подключения — [examples/mcp-client.json](../examples/mcp-client.json). Все агенты должны использовать один абсолютный путь к `config.json`, чтобы разделять очередь. Формат подключения зависит от клиента.

```json
{
  "mcpServers": {
    "astra": {
      "command": "C:\\vs\\PromCut\\AstraMcp\\publish\\win-x86\\AstraMcp.exe",
      "args": ["--config", "C:\\vs\\PromCut\\AstraMcp\\config.json"]
    }
  }
}
```

Ручной запуск для подключения Inspector:

```powershell
.\publish\win-x86\AstraMcp.exe --config .\config.json
```

Не вводите обычный текст в stdin: этот поток обслуживает MCP. Журнал сервера — `.data/logs/mcp-YYYYMMDD-PID.log` и stderr; stdout содержит только протокол.

## Конфигурация

[config.json](../config.json) читается при запуске. Относительные пути разрешаются относительно самого JSON-файла; изменения применяются после перезапуска MCP.

| Поле `Astra` | Назначение |
| --- | --- |
| `ExecutablePath` | Полный путь к `Astra.exe`; по умолчанию `C:\Program Files (x86)\Astra R-Nesting\Astra.exe` |
| `DataDirectory` | Общие SQLite-очередь, исходные файлы, результаты и логи |
| `ExportDirectory` | Каталог, в который Астра экспортирует XML при выходе |
| `TimeoutSeconds` | Общий предел выполнения, от 1 до 3600 секунд |
| `PollIntervalMilliseconds` | Интервал проверки очереди и отмены, от 25 до 5000 мс |
| `ProfileReady` | Явное подтверждение настройки профиля Астры; не заменяет реальный smoke-тест |

Отсутствие исполняемого файла не мешает запуску MCP, диагностике и проверке XML, но блокирует приём расчётов. Одна очередь закрепляется за конкретными путями EXE и экспорта; несовместимая конфигурация с тем же `DataDirectory` отклоняется.

Перед **каждым новым расчётом** сервер находит процессы по имени настроенного EXE, проверяет полный путь и останавливает совпавшие процессы по PID. Это явное требование владельца проекта. Открытый несохранённый заказ при таком завершении теряется. Используйте выделенную тестовую сессию Астры. Ошибка проверки пути или остановки PID блокирует новый запуск. При отмене/тайм-ауте завершается только дочерний процесс, принадлежащий текущему заданию.

## Профиль Астры

В `Сервис → Параметры` должны быть настроены:

1. `Управление → При запуске`: **Обработать параметры командной строки**.
2. `Управление → При выходе`: режим без вопроса о сохранении, включён **Экспортировать файл**, имя **`*.xml`**.
3. `Расположение`: каталог обмена соответствует абсолютному `ExportDirectory`. Проверьте его также в поле каталога экспорта при выходе.
4. Стартовые советы отключены; внешняя команда при выходе пустая; передача в производство не включена.
5. Для сравнений используются отдельные каталоги заказов и справочников. Все листы задаются во входном XML; автоматическое добавление листов из постороннего склада должно быть отключено.
6. `Формат`: единицы длины и ширины — **мм**. Количество десятичных знаков задаётся в Астре; значение **0 допустимо**. Для текущей проверки менять эту настройку не требуется. Адаптер принимает размеры длины и ширины, округлённые в результате до ближайшего целого миллиметра.
7. Для автоматической обработки частичного раскроя включите `Управление → Действия по умолчанию → Не сообщать о проблемах при раскрое`. Иначе сообщение о неразмещённых деталях может блокировать завершение до тайм-аута. Неразмещённые детали проверяются по результату и остаются в отчёте MCP.

На проверяемой машине тестовые каталоги располагаются внутри `.data/astra-profile`, обмен — `.data/astra-exchange`. Настройки Астры относятся к пользователю Windows и сохраняются самой программой. MCP не устанавливает и не распространяет Астру, не меняет её реестр при запуске и не скрывает диалоги. Исходные пользовательские заказы не нужны для smoke-теста.

На рабочей машине профиль проверен реальными расчётами и в `config.json` установлено `ProfileReady=true`. При переносе на другую машину сначала используйте `false`, настройте профиль и проведите проверку. Флаг — утверждение оператора о готовности, а не автоматическая проверка всех настроек приложения.

Для проверенного legacy-профиля установленной Астры настройка командного экспорта воспроизводится кодом:

```powershell
.\scripts\configure-astra-profile.ps1 -ConfigurationFile config.json
```

Скрипт выполняется при закрытой Астре в том же пользовательском контексте Windows, что и MCP. Он задаёт каталог XML-экспорта, отдельную тестовую базу внутри `.data/astra-profile/database`, отключает добавление листов из постороннего склада и блокирующее уведомление о частичном раскрое. Старые значения сохраняются в `.cache/profile-configuration`. Другие профили и версии требуют проверки: скрипт рассчитан на обнаруженный `HKCU\Software\Technos\Астра Раскрой\Settings`. Режим обработки командной строки должен соответствовать пункту 1 выше.

## Инструменты и ресурсы

| Инструмент | Поведение |
| --- | --- |
| `get_capabilities` | Версия и путь EXE, доступность файла, профиль, тайм-аут, ограничения |
| `validate_order(xml)` | Проверка поддерживаемого подмножества исходного XML без Астры |
| `submit_order(xml, requestKey)` | Постановка в очередь с немедленным возвратом `jobId` |
| `get_job(jobId)` | Короткий отчёт о состоянии, количестве деталей, PID и ошибке |
| `get_result(jobId)` | Короткий отчёт и ссылка на XML; содержимое XML не вставляется в ответ инструмента |
| `cancel_job(jobId)` | Отмена ожидания или запрос остановки текущего расчёта |

Описания инструментов и параметров предназначены для модели. Аннотации отмечают операции чтения, идемпотентность и операции с побочными эффектами. Повтор `submit_order` с тем же ключом и тем же текстом XML возвращает прежнее задание; другой XML с этим ключом отклоняется. Новый ключ означает новый расчёт, даже если заказ совпадает.

Подробные файлы читаются явно через ресурс `astra://jobs/{jobId}/{kind}`. Допустимые `kind`: `input`, `execution_input`, `result`, `manifest`, `log`. Произвольные пути не принимаются. XML результата доступен только для `Succeeded`; лог ограничен последними 32 000 символов. Ошибки инструмента возвращаются с `isError=true` и объяснением, пригодным для следующего действия модели.

Очередь SQLite и немедленные транзакции обеспечивают единственный захват задания. Файловая блокировка на EXE в текущем пользовательском TEMP защищает и разные MCP-процессы/каталоги от взаимного завершения расчётов. Заброшенный `Running` после получения блокировки помечается `Failed`, без скрытого повторного расчёта. Идентификатор и время старта прежнего процесса остаются в манифесте. Следующий запуск выполняет предусмотренную остановку существующих PID.

## XML и результаты

Поддерживается один `data/data_order`, прямоугольные детали, уникальные имена групп материалов, явные конечные положительные количества листов и деталей. Размеры — положительные десятичные миллиметры с точкой. Контуры, готовые карты, блоки изменения склада и сброса справочников отклоняются. Это ограниченный контракт адаптера, а не валидатор всех возможностей Астры.

В `.data/jobs/<jobId>/` сохраняются `input.original.xml`, UTF-8 копия `input.astra.xml` с уникальным именем заказа, неизменённый `result.astra.xml`, `manifest.json`, `execution.log`, `native-stdout.log` и `native-stderr.log`. Входные артефакты записываются до публикации задания в очереди. SHA-256 относится к UTF-8 представлению текста, полученного через MCP; сохранение оригинального XML учитывает объявленные UTF-8/Windows-1251.

Успех требует нулевого кода выхода и свежего экспортного имени, совпадения имени заказа, материалов, толщины, разрешений поворота и допустимых количеств деталей/листов. Длина и ширина деталей и листов должны совпадать точно либо быть представлены в экспорте ближайшим целым миллиметром: целочисленный результат допускает отличие до 0.5 мм включительно; для середины допускаются оба направления округления. `600.1 → 600` и `600.8 → 601` допустимы, `600.8 → 600` и изменение целого `600 → 601` — нет. Дробные значения результата сравниваются точно; это не общий допуск 0.5 мм. Толщина остаётся точной. Правило не изменяет входные размеры, координаты или сохранённый XML результата.

Количество физических копий учитывает `nesting_plan/@quantity`. Повторяющиеся номера различаются по материалу, сборке, размерам и разрешению поворота. Неразмещённые детали вычисляются как остаток исходного спроса; они не превращают частичное допустимое решение в ошибку запуска.

В ручном экспорте [MCP decimal shelf.xml](../examples/MCP%20decimal%20shelf.xml) обнаружен `list_cuts/cut` с координатами концов резов `x1`, `x2`, `y1`, `y2` и необязательным `type`. В более новой копии [MCP decimal shelf.coordinates.xml](../examples/MCP%20decimal%20shelf.coordinates.xml) есть и координаты размещённых деталей `x`/`y`. Настройка их включения и явное дерево резов пока не установлены. Сервер сохраняет XML без изменений; геометрическая корректность раскладки и единицы ненулевого `cut_length` такой проверкой не подтверждаются. У одинаковой карты в двух экспортных копиях `cut_length` различается, поэтому метрика пока требует проверки. Предел входного/разбираемого XML — 4 млн символов; предел чтения файла — 16 МБ. При отсутствии экспорта или зависшем диалоге задание получает ошибку/тайм-аут с диагностикой.

Ручная проверка 01.11.2026 показала, что `600.1 × 400.2` экспортируется как `600 × 400`, а `600.8 × 400.9` с точкой — как `601 × 401`. Пользователь подтвердил настройку 0 десятичных знаков и решил считать целочисленное представление нормальным. Адаптер принимает эти результаты по описанному правилу; проверка дробной точности отложена. Проба с запятой не соответствует запрошенному размеру D2 даже после округления; XML-вход MCP по-прежнему требует точку. Кромка `ABS 0.4` отсутствует в результате. Сохранённые файлы включены в регрессионные тесты. Подробности — [docs/manual-export.md](manual-export.md). Затем пользователь разрешил автоматический запуск и остановку Астры: восемь реальных заказов прошли MCP, проверку количества и независимую проверку координат. Итоги — [docs/native-verification.md](native-verification.md).

## Сборка и проверка

Для разработки нужны .NET SDK из `global.json` и Node.js 22.19+ для Inspector. Установка библиотек выполняется кодом; административные права не требуются. Версии NuGet и npm закреплены lock-файлами.

```powershell
.\scripts\build.ps1
```

Скрипт выполняет locked restore, тесты отдельного проекта, самостоятельную публикацию Windows x86, `npm ci` и пять проверок Inspector. Для сборки только .NET используйте `-SkipInspector`.

Тесты проверяют XML, количество физических деталей, повороты, конкурирующие очереди, идемпотентность, отмену, тайм-аут, восстановление после прерывания, реальные тестовые дочерние процессы и MCP через настоящий stdio-клиент. Они не запускают установленную Астру. Журналы этапов red/green находятся в `.cache/tdd` рабочей машины.

Набор из восьми мебельных заказов — [examples/batch](../examples/batch/README.md), генератор — `node scripts/generate-orders.mjs`. Все заказы проверяются через `validate_order` по настоящему MCP stdio. `McpBatchTests` дополнительно проходят путь submit → очередь → отдельный тестовый EXE → get_result → XML-ресурс, проверяют идентичность байтов сохранённого экспорта, повтор запроса, конфликт ключа, отмену, тайм-аут и неверный результат. Для этих сквозных проверок EXE воспроизводит известный экспорт, не выполняя оптимизацию. Файлы и манифесты сохраняются в `.cache/mcp-batch`; их нельзя считать результатами новых расчётов установленной Астрой.

```powershell
npm run test:inspector
npm run inspector -- --config .cache/inspector/session.json
```

Реальные расчёты выполняет официальный **.NET MCP-клиент**, Node-клиент для этого не используется:

```powershell
dotnet run --project tools/Verification/Verification.csproj -- . config.json
dotnet run --project tools/Verification/Verification.csproj -- . config.json 04-rotation-required
```

Первый запуск отправляет все восемь заказов в очередь, второй — один выбранный пример. Клиент проверяет повтор запроса, терминальные статусы, количества, чтение XML через MCP-ресурс, границы листов, пересечения, зазоры под пропил и координаты резов. Результаты сохраняются в `examples/batch/results/<run>/`: неизменённый `result.astra.xml`, входной XML, манифест, лог и `geometry.json` для каждого заказа, общий `report.json`. Это тест установленной Астры, он запускает и завершает её процессы. Обычный `dotnet test` запускает только тестовый EXE и не требует Астры.
